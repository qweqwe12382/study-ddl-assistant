## 🧭 一、项目概述

### 1.1 项目名称

**学习DDL与资料管理智能体**

暂定产品名称：**学伴管家**。

### 1.2 对应赛题

中兴赛道——命题四：学习DDL与资料管理智能体。

### 1.3 项目定位

本项目面向在校大学生，解决课程资料分散、课程通知难以整理、作业和考试截止日期容易遗忘、复习任务缺少规划等问题。

系统通过文件上传、OCR识别、文本理解和结构化管理，将学生手中的课程通知、课程讲义、作业要求、考试安排和复习资料转化为可检索、可提醒、可规划的个人学习数据。

项目的核心闭环为：

> 资料入库 → 内容识别 → 自动分类与标签化 → DDL提取 → 查询检索 → 任务提醒 → 复习计划生成 → 结果导出

系统不追求一开始覆盖所有学习场景，而是优先完成一个稳定、可演示、可复用的个人学习管理闭环。

## 🎯 二、项目背景与用户痛点

### 2.1 现实问题

大学生的课程资料通常来源复杂，包括课程群通知、学习平台公告、教师发放的PDF、Word文档、截图、网盘文件和纸质材料。不同课程的通知格式不统一，截止日期容易被忽略，资料也很难长期保持清晰的目录结构。

常见问题包括：

1. 作业、实验、报告和考试时间分散在不同群聊或文件中。
2. 学生需要手动阅读通知并记录DDL，整理成本较高。
3. 资料文件名不规范，过一段时间后难以判断文件内容。
4. 复习资料与课程章节之间缺乏关联。
5. 学生知道任务很多，但无法快速判断近期最重要的任务。
6. 使用普通网盘只能存储文件，无法理解文件内容并辅助安排学习。

### 2.2 目标用户

主要用户为：

- 在校本科生和研究生；
- 同时修读多门课程、任务较多的学生；
- 需要管理实验报告、课程作业和考试复习资料的学生；
- 新生或对校园学习工具不熟悉的用户。

后续可以扩展到助教或班级学习组织者，但第一版只聚焦个人用户，以降低权限、协作和隐私管理的复杂度。

### 2.3 核心用户场景

#### 场景一：从课程通知中提取DDL

学生上传一张课程群通知截图，系统识别课程名称、任务内容、截止时间和提交要求，并生成一条待办任务。

#### 场景二：自动整理课程资料

学生上传多个PDF和Word文件，系统根据文件内容判断课程、资料类型和章节，并生成课程资料目录。

#### 场景三：自然语言检索资料

学生输入“查找数据结构中关于二叉树的资料”，系统返回相关文件、匹配章节和文件来源。

#### 场景四：生成近期任务清单

系统根据当前日期、截止时间和任务优先级，生成“本周待完成任务”和“即将逾期任务”。

#### 场景五：生成考试复习计划

学生输入考试日期、每天可用学习时间和重点章节，系统生成分阶段复习计划。

#### 场景六：导出学习安排

学生将DDL清单导出为CSV，将资料目录和复习计划导出为Markdown，便于备份或继续使用。

## ✅ 三、项目目标

### 3.1 总体目标

完成一个可运行的个人学习智能体：它能够从资料和任务变化中持续感知学习状态，提取并关联 DDL，结合截止时间、任务工作量和个人可用时间判断风险，提出有依据的行动候选，经用户确认后执行，并根据完成结果调整后续计划。

### 3.2 比赛版本目标

当前题目基础能力已经完成，M8 比赛版本进一步达到以下目标：

1. 上传资料后由本地规则自动形成课程、标签和 DDL 候选，并进入统一学习收件箱。
2. 每个候选字段保留文件名或正文来源、置信度和复核状态。
3. 用户可以设置每周可用时间、偏好时段、单日上限和课程权重。
4. 任务包含预计用时和剩余用时，系统能够识别容量不足、临期、逾期和同日冲突。
5. 首页提供最多 3 条“今日行动”，每条说明原因、来源、预计用时和风险。
6. 智能体建议具有待确认、已接受、已忽略、已执行、已失败和已失效生命周期。
7. 接受建议后由服务端校验和执行，并返回真实执行回执；重复请求不重复产生业务数据。
8. 新 DDL、任务完成、逾期和实际用时变化能够触发计划调整候选。
9. 用户可以编辑、拒绝或忽略任何建议，智能体不会直接覆盖人工计划。
10. 外部 AI 继续按次授权；后台事件只使用本地能力，不静默外发资料。
11. 默认界面让普通大学生先看清今天要做什么、为何优先和哪里需要确认；证据、历史、完整筛选及高级配置可在详细视图展开，高风险事实不因简化隐藏。

### 3.3 成功指标

当前阶段以可执行的产品行为作为成功标准，不提前整理比赛评测案例：

| 成功标准 | 判定方式 |
| --- | --- |
| 主动感知 | 资料、任务或计划变化会形成可追溯事件，并触发对应建议刷新 |
| 有据判断 | 每条重要建议都包含来源对象、原因码、时间依据和容量依据 |
| 受控行动 | 模型和前端不能直接修改数据库，只能提交白名单候选并由服务端执行 |
| 可恢复 | 建议过期、重复接受、业务状态变化或执行失败不会留下部分数据 |
| 会调整 | 新 DDL、逾期或完成反馈能够产生计划差异候选，而不是静态重复生成 |
| 用户可控 | 学习偏好和反馈可查看、修改、重置；人工计划和已完成内容不被自动覆盖 |
| 一眼可用 | 默认简洁视图聚焦行动、风险与确认入口；详细视图保留证据和完整配置，桌面与手机均无页面级横向溢出 |

这样可以避免项目受第三方平台接口、账号权限和隐私风险影响。

## 🧩 五、核心功能设计

### 5.1 首页与工作台

首页升级为 Agent Center，优先展示可行动内容：

- 学习收件箱：新资料、待确认 DDL、解析失败和冲突字段；
- 今日三件事：最多 3 条带原因、来源、预计用时和风险的行动；
- 风险中心：容量不足、同日多 DDL、临期、逾期和计划偏离；
- 智能体建议流：接受、编辑后接受、忽略和查看过期原因；
- 执行回执：展示真实受影响的任务或计划，以及失败原因；
- 现有任务统计、最近资料和计划进度作为辅助信息保留。

首页必须回答“系统发现了什么、为什么重要、建议做什么、做完发生了什么”，而不是只展示文件和任务数量。

### 5.2 资料上传与入库

用户可以点击上传，也可以将多个文件拖入上传区域。上传后系统完成以下处理：

1. 校验文件格式和大小。
2. 保存原始文件或其安全副本。
3. 提取文件文本。
4. 对图片执行OCR。
5. 识别文件可能对应的课程。
6. 自动生成资料类型和关键词标签。
7. 使用文件名和正文判断是否包含任务、考试或截止日期信息。
8. 默认使用本地规则自动生成结构化候选并写入学习收件箱。
9. 将候选字段的来源、置信度、冲突和复核原因展示给用户确认。

建议保留原始文件名、上传时间和处理状态，方便用户追溯。

### 5.3 结构化信息抽取

从课程通知中优先提取以下字段：

| 字段 | 说明 | 是否必填 |
|---|---|---|
| course_name | 课程名称 | 否 |
| task_name | 任务名称 | 否 |
| task_type | 作业、实验、报告、考试等 | 否 |
| due_date | 截止日期 | 否 |
| due_time | 截止时间 | 否 |
| submit_method | 提交方式 | 否 |
| chapter | 相关章节 | 否 |
| priority | 优先级 | 否 |
| source_file | 来源文件 | 是 |
| source_field | 字段来自文件名或正文 | 是 |
| confidence | 识别置信度 | 是 |
| need_review | 是否需要人工确认 | 是 |

重要原则：日期字段不应只依赖大模型直接输出。系统应在模型提取后进行日期格式校验、时间合理性校验和原文回溯，并将低置信度结果标记为“待确认”。

### 5.4 课程资料分类

默认资料类型可以设置为：

- 课程大纲；
- 课堂讲义；
- 教材或阅读材料；
- 作业要求；
- 实验资料；
- 复习资料；
- 习题与答案；
- 考试通知；
- 其他。

分类结果允许用户手动修改。系统应始终保留“原始文件”和“当前分类”两个概念，避免模型判断错误后无法恢复。

### 5.5 资料检索

第一版采用“关键词检索+结构化筛选”的方式，稳定且容易实现。支持以下条件：

- 课程名称；
- 文件类型；
- 标签；
- 上传时间；
- 是否包含DDL；
- 章节或知识点；
- 文件名和正文关键词。

检索结果应显示匹配依据，例如“匹配标签：排序”“匹配正文：时间复杂度”，并关联相关任务、计划项和智能体建议。向量检索不是当前优先项，只有在结构化检索无法满足真实场景时再引入。

### 5.6 DDL任务管理

每条任务至少包含：

- 任务名称；
- 所属课程；
- 截止日期和时间；
- 来源资料；
- 优先级；
- 当前状态；
- 备注；
- 预计用时和剩余用时；
- 创建时间和更新时间。

任务状态建议使用：

```text
未开始 → 进行中 → 已完成
未开始 → 已逾期
进行中 → 已逾期
```

系统每天根据当前时间自动判断是否逾期。用户手动标记完成后，不应再次被系统自动改为逾期。预计用时、剩余容量、截止时间和课程权重共同用于生成风险与行动候选；缺失预计用时时只能提示补充，不能伪造精确容量结论。

### 5.7 复习计划生成

用户输入：

- 目标课程；
- 考试日期；
- 每天可学习时间；
- 已掌握章节；
- 薄弱章节；
- 是否需要安排模拟练习。

系统输出：

- 每日或每阶段学习任务；
- 章节复习顺序；
- 预计用时；
- 练习和回顾安排；
- 计划风险提示。

复习计划应允许用户调整日期和任务。新 DDL、任务完成、逾期和实际用时变化后，智能体可以生成计划差异候选，但不能直接覆盖用户已有 DDL、已完成计划项或人工锁定内容。用户接受后才执行重排，并保存调整前后快照和执行回执。

### 5.8 导出功能

至少支持：

#### CSV导出

适合导出任务清单，字段包括：任务名称、课程、截止日期、优先级、状态、来源文件。

#### Markdown导出

适合导出资料目录和复习计划，例如：

```markdown
# 数据结构课程资料

## 待完成任务

- [ ] 完成实验三：二叉树遍历
  - 截止时间：2026-10-15 23:59
  - 来源：课程通知.png

## 复习计划

- 10月1日：复习树的基本概念
- 10月2日：练习二叉树遍历
```

#### iCal导出（增强功能）

用于将DDL导入系统日历。需要注意时区、全天事件和时间缺失等情况。

## 🏗️ 六、系统总体架构

### 6.1 架构分层

建议采用前后端分离的轻量架构：

```text
用户
  ↓
Web前端
  ↓
FastAPI后端
  ├── 文件上传服务
  ├── 文本/OCR处理服务
  ├── AI信息抽取服务
  ├── 资料分类与检索服务
  ├── DDL任务服务
  ├── 复习计划服务
  └── 文件导出服务
  ↓
SQLite数据库 + 本地文件存储
```

### 6.2 推荐技术栈

| 层级 | 推荐方案 | 说明 |
|---|---|---|
| 前端 | Vue 3 + Vite | 适合快速搭建交互界面 |
| UI组件 | Element Plus | 提供表格、日期选择器、上传组件 |
| 后端 | Python FastAPI | 接口清晰，便于调用AI和文件解析库 |
| 数据库 | SQLite | 比赛演示和单用户场景足够 |
| ORM | SQLAlchemy或SQLModel | 管理数据表和查询 |
| PDF解析 | PyMuPDF | 提取PDF文本和页面信息 |
| Word解析 | python-docx | 读取.docx内容 |
| OCR | PaddleOCR或其他可用OCR方案 | 识别课程通知截图 |
| AI能力 | 大模型API | 信息抽取、分类、检索问答、计划生成 |
| 检索 | SQLite全文检索或基础关键词检索 | MVP阶段优先稳定实现 |
| 导出 | Python csv、Markdown模板、icalendar | 实现多格式导出 |
| 部署 | 本地运行或轻量云服务器 | 以可访问和易演示为目标 |

如果部署环境不方便安装OCR或向量数据库，MVP可以先使用文本文件和预设演示数据完成主要流程，再逐步增加图片识别能力。

### 6.3 实现所需工具与平台

本项目建议优先采用“本地开发 + Git版本管理 + 云端或本地演示”的方式。第一版不要求同时接入多个平台，先保证核心功能可运行，再根据比赛展示需要增加部署和协作能力。

#### 6.3.1 必需工具

| 类别 | 工具或平台 | 用途 | 必要性 |
|---|---|---|---|
| 操作系统 | Windows、macOS或Linux | 项目开发和运行环境 | 必需 |
| 代码编辑器 | Visual Studio Code | 编写前端、后端和文档 | 必需 |
| 版本管理 | Git | 代码提交、版本回退和协作 | 必需 |
| 代码托管 | GitHub、GitLab或Gitee | 远程备份和团队协作 | 推荐 |
| Python环境 | Python 3.11或兼容版本 | 后端、文件解析和AI服务 | 必需 |
| JavaScript环境 | Node.js LTS和npm | 前端依赖安装与构建 | 必需 |
| 数据库工具 | SQLite和SQLite浏览器 | 查看和调试业务数据 | 推荐 |
| API调试工具 | Apifox、Postman或Insomnia | 调试后端接口 | 推荐 |
| 浏览器 | Chrome或Edge | 前端调试和比赛演示 | 必需 |

#### 6.3.2 前端开发工具

建议使用以下组合：

- Vue 3：构建页面和交互逻辑；
- Vite：创建项目、启动开发服务器和打包；
- Element Plus：提供上传、表格、弹窗、日期选择器等组件；
- Axios：调用后端接口；
- Vue Router：管理页面路由；
- ESLint和Prettier：统一代码风格和减少低级错误；
- Chrome DevTools：调试网络请求、页面布局和运行性能。

前端第一版不建议引入过多UI库。上传、资料列表、DDL列表、复习计划和导出按钮使用同一套组件风格即可。

#### 6.3.3 后端开发工具

建议使用以下组合：

- FastAPI：创建REST API和文件上传接口；
- Uvicorn：运行FastAPI开发服务器；
- Pydantic：校验接口输入和AI结构化输出；
- SQLModel或SQLAlchemy：操作SQLite数据库；
- Alembic：管理数据库结构变更，项目规模较小时可以后置；
- pytest：编写后端单元测试和接口测试；
- python-dotenv：读取本地环境变量；
- ruff或flake8：检查Python代码质量。

#### 6.3.4 文件处理与OCR工具

## 🤖 八、AI处理流程与可靠性设计

### 8.1 文件处理流程

```text
上传文件
  ↓
格式和大小校验
  ↓
文本提取或OCR
  ↓
文本清洗
  ↓
AI结构化抽取
  ↓
日期、字段、格式校验
  ↓
置信度评估
  ↓
用户确认或修改
  ↓
写入数据库
```

### 8.2 结构化输出要求

要求大模型只返回固定JSON结构，不直接返回散文式结果。例如：

```json
{
  "course_name": "数据结构",
  "tasks": [
    {
      "task_name": "实验三：二叉树遍历",
      "task_type": "实验",
      "due_date": "2026-10-15",
      "due_time": "23:59",
      "priority": "高",
      "source_quote": "请于10月15日前提交实验三报告",
      "confidence": 0.94,
      "need_review": false
    }
  ],
  "material_type": "作业要求",
  "tags": ["二叉树", "实验", "报告"]
}
```

### 8.3 日期识别规则

日期处理是本项目最容易出错的部分，建议使用以下策略：

1. 明确年份时直接使用原文年份。
2. 只有月日而没有年份时，结合上传时间和学期配置推断年份。
3. 推断出的年份必须在界面中标记为“系统推断”。
4. 出现“下周一”“本周五”等相对日期时，显示计算依据。
5. 出现多个日期时，分别判断是发布时间、开始时间还是截止时间。
6. 识别不到具体日期时，不生成虚假的DDL，只提示用户手动补充。
7. 截止日期早于发布时间或明显异常时，标记为待确认。

### 8.4 置信度和人工确认

建议采用三档机制：

- 高置信度：直接进入任务列表，但允许用户修改。
- 中置信度：进入“待确认”区域，等待用户确认。
- 低置信度：只保存原文和识别建议，不自动创建正式任务。

即使模型置信度较高，也应保留来源文件和原文片段，避免用户无法判断信息从何而来。

### 8.5 防止模型幻觉

系统生成的内容分为三类：

1. **事实型信息**：课程名、DDL、提交方式等，必须来自用户上传资料或用户手动输入。
2. **辅助型信息**：标签、摘要、资料分类，可以由模型生成，但需要允许修改。
3. **建议型信息**：复习计划、优先级建议，可以由模型生成，但必须标注为建议。

对于第一类信息，不应允许模型凭空补全。找不到依据时应输出“未识别”或“需要确认”。

## 🎬 十三、演示方案

### 13.1 推荐演示故事

演示用户是一名同时学习数据结构、数据库和高等数学的学生。课程通知散落在群聊截图和PDF文件中，学生希望快速整理近期任务并制定期末复习计划。

### 13.2 3—5分钟演示流程

#### 第一幕：展示问题（约20秒）

展示几份杂乱的课程通知、PDF和截图，说明任务和资料分散在不同位置。

#### 第二幕：上传资料（约50秒）

上传一张课程通知截图。系统显示OCR进度，并识别出课程、实验名称和截止日期。

#### 第三幕：人工确认（约30秒）

展示结构化结果和原文依据。修改一个字段并确认入库，体现系统可控和可纠错。

#### 第四幕：查看DDL（约40秒）

进入任务页面，展示未来7天任务、优先级和任务状态。将一个任务标记为已完成。

#### 第五幕：检索资料（约40秒）

输入“查找二叉树相关资料”，展示匹配文件、标签和原文片段。

#### 第六幕：生成复习计划（约50秒）

输入考试日期和每日学习时间，生成复习计划，并修改其中一个计划项。

#### 第七幕：导出结果（约20秒）

导出CSV任务清单或Markdown复习计划，说明资料和任务可以带走，不被系统锁定。

### 13.3 演示注意事项

- 使用提前准备好的稳定演示数据。
- 网络不稳定时提供本地演示模式。
- 不展示真实姓名、学号、手机号或私人聊天记录。
- 演示时主动展示识别依据和人工确认机制。
- 不把大模型输出描述为绝对正确。
- 准备一份演示失败时的备用数据。

## 🔐 十四、数据安全与合规设计

### 14.1 数据来源

比赛版本使用：

- 自行编写的模拟课程通知；
- 经脱敏处理的公开课程资料；
- 团队自行制作的演示文件；
- 不包含真实个人信息的测试数据。

### 14.2 隐私保护

- 不采集真实学号、手机号和身份证号。
- 上传文件仅用于当前用户的资料管理。
- API密钥通过环境变量配置，不写入代码仓库。
- 文件名和文本内容在日志中脱敏。
- 删除资料时同步删除对应的本地文件。
- 对上传文件设置大小和类型限制。
- 生产部署时使用HTTPS和访问鉴权。

### 14.3 AI生成内容说明

系统对课程通知中的事实信息提供原文来源；复习计划和优先级属于辅助建议，用户应根据实际课程要求进行确认。系统不替代教师、教务部门或学校官方通知。

### 14.4 失败兜底

当系统无法识别或无法确定信息时：

1. 保留原始文件。
2. 展示识别失败原因。
3. 提供手动录入入口。
4. 允许重新识别。
5. 对学校官方信息提示用户以原通知为准。

## ⚠️ 十五、主要风险与应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| OCR识别错误 | DDL错误 | 展示原文、置信度和人工确认 |
| 大模型返回格式不稳定 | 数据无法入库 | 使用JSON Schema或程序校验 |
| 日期识别错误 | 用户错过任务 | 异常日期拦截，禁止低置信度自动入库 |
| API调用失败 | 智能功能不可用 | 提供手动录入和演示数据模式 |
| 文件解析失败 | 资料无法导入 | 支持重试并提示具体原因 |
| 数据库损坏 | 数据丢失 | 提供备份和导出功能 |
| 开发范围过大 | 无法按时完成 | 优先保证MVP闭环 |
| 网络部署不稳定 | 现场无法演示 | 准备本地运行版本和录屏备份 |
| 用户上传敏感信息 | 合规风险 | 演示使用脱敏数据并限制日志记录 |
